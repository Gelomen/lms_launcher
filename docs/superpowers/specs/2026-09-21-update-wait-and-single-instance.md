# 规格：修复更新等待条件与单实例锁失效（多实例共存）

> 日期：2026-09-21 · 分支：master · 状态：待实现
> 关联：`2026-09-21-update-relaunch-detached-process.md`（同日 DETACHED_PROCESS 修复）。
> 本文是那次修复**真机验收**（v0.3.1 安装目录 → v0.3.2-rc.1 release）中暴露的两个**独立**缺陷。
> DETACHED 修复本身未被证伪 —— 本次流程根本没走到它的第 6 步。

## 背景

真机验收流程：build → 覆盖 ps1 到 `D:\AI\LMS-Launcher` → 升级 v0.3.2-rc.1 打包 → GitHub release
→ 旧版应用检测到新版本 → 下载 → 点「重启」→ 计划任务拉起 `lms-launcher-update.ps1`。

实际结果：脚本日志只有两行便中止，更新完全未发生（应用仍是 0.3.1）：

```
2026-09-21 20:10:38 [INFO] 更新脚本启动 · zip=…\lms-launcher-update.zip · dir=D:\AI\LMS-Launcher
2026-09-21 20:11:39 [ERROR] 等待 lms_launcher.exe 退出超时（60s），中止更新
```

即：脚本第 1 步（等待旧进程退出）永远无法满足。两个互相独立、各自都足以造成该结果的原因如下。

## 缺陷 1：等待的是「机器上任意同名进程」，而非安装目录里的那个

### 根因

`scripts/lms-launcher-update.ps1:57-66`：

```powershell
$p = Get-Process -Name 'lms_launcher' -ErrorAction SilentlyContinue
if ($null -eq $p) { break }   # 只有「全机器再无任何 lms_launcher 进程」才通过
```

按**进程名**匹配，与安装目录无关。任何时候只要存在另一个同名实例（开发构建产物、另一份解压副本、
用户忘记关闭的托盘实例），循环就永远无法满足，60 秒后必然中止。

### 证据（真机实测，2026-09-21 20:21:36，更新失败后）

| 判定方式 | 结果 |
|------|------|
| `Get-Process -Name 'lms_launcher'`（现行实现） | **3 个** |
| 按安装目录路径过滤（`Path -ieq <installDir>\lms_launcher.exe`） | **0 个** |

那 3 个进程全部来自 `D:\AI\Workspace\lms_launcher\dist-release\win-unpacked\lms_launcher.exe`，
`StartTime = 20:08:12` —— 早于脚本等待窗口（20:10:38–20:11:39），且调查时仍存活，
因此逻辑上**必然**完整覆盖了整个 60 秒等待期。安装目录自己的实例早已退出（路径过滤 = 0），
本应立即通过并完成更新。

### 方案

等待目标收紧为「**安装目录内的 `lms_launcher.exe`**」——只有它锁着待覆盖的文件；
其他路径的同名实例不占用本次安装目录，等它们只会误超时。附带两项加固：

1. 超时日志打印**残留进程详情**（PID + 启动时间），下次一眼定位；
2. 检测到「其他路径的同名实例」时记一条 `[INFO]`（明确说明不影响本次更新），避免再被误读为卡死。

路径比较用 `-ieq`（大小写不敏感）；`$InstallDir` 经 `[System.IO.Path]::GetFullPath()` 归一化
（顺带覆盖尾部分隔符与相对路径）；取 `$_.Path` 时逐进程 `try/catch`。

**读不到路径时的默认方向（2026-09-21 独立审查 I-1 修订）**：`.Path` 读不到（权限不足 / 枚举与退出
之间的竞态）时按「**可能属于本安装目录**」保守处理并记 `[INFO]` —— 宁可误等多 60s 直至超时中止，
也不能误跳过等待去覆盖可能仍在运行的 exe（覆盖被占用的文件会抛异常，留下混版本的安装目录且不可回滚）。
初版实现取的是相反默认（「读不到即归入其他」），审查指出它把不确定性代价转嫁给了用户的安装目录，已纠正。

## 缺陷 2：单实例锁失败路径缺少确定性退出（防御性加固）

### 现象

真机现场除执行更新的实例（已按设计 `app.exit(0)` 退出）之外，还存在一个**不持有单实例锁、无可见窗口、
已存活 27 分钟以上**的同名实例：`dist-release\win-unpacked\...\lms_launcher.exe`（PID 2872，
`StartTime = 20:08:12`）。判定它「不持锁」的依据是实测：在它运行期间新启动的实例**能正常拿到锁并长期
存活**（20:35 探针：存活 ≥60s、有可见窗口、4 个子进程）。它正是把更新脚本卡死（缺陷 1）的那个进程。

### 机制

`src-main/main.ts` 单实例锁处的注释承诺「第二个进程拿不到锁时返回 false，**立即退出**」，而本次修订前的
实现是 `app.quit()`（HEAD 版 `main.ts:30-31`）；同文件把窗口「关闭」实现为「隐藏到托盘」（改后 `main.ts:199`）：

```js
win.on('close', (e) => { e.preventDefault(); win.hide(); });   // 关闭 = 隐藏到托盘
```

`app.quit()` 是优雅退出：它会先关闭所有窗口，一旦窗口 `close` 的 `preventDefault()` 生效，退出流程即被取消
→ 该实例既拿不到锁、也不退出，成为「不持锁的常驻实例」。这类实例堆在托盘里，正是缺陷 1 的温床。

### 证据强度（如实标注）

| 证据 | 结果 |
|------|------|
| 现场实例 A：不持锁、无窗口、常驻 ≥27 分钟 | **实证**（间接证明该分支的产物真实存在，且新实例可照常启动） |
| 锁失败场景探针，在真实打包产物上重复 8 轮 | **8/8 均在 ~2.3s 退出，未复现常驻侧** |

即常驻分支受时序影响（第二实例是否在 `app.quit()` 被处理前已完成窗口创建），本机探针未能稳定复现。
因此本项定位为**消除不确定性的防御性加固**，而非「有可复现失败用例」的修复 —— 它的价值在于让
「拿不到锁」这条路径的行为确定化，与代码注释承诺的语义一致。

### 方案

锁失败路径改用 `app.exit(0)`：立即终止整个进程，不触发窗口 `close` / `before-quit` / `will-quit`，
因此不受「关闭=隐藏到托盘」影响。与 `run_update`（`main.ts:583`）、`exit_app`（`main.ts:326`）
既有的 `app.exit(0)` 用法一致。

## 缺陷 3（同类）：verify-relaunch.ps1 的 C1 也按进程名取进程

`scripts/verify-relaunch.ps1:49` 的 `C1 新版存活` 用
`Get-Process -Name 'lms_launcher' | Select-Object -First 1` 取进程，多实例场景下可能拿到别的实例，
导致断言错位（该脚本已有 `-InstallDir` 参数，本题恰好是它的主场）。改为按 `-InstallDir` 路径过滤。

## 改动面

| 文件 | 改动 |
|------|------|
| `scripts/lms-launcher-update.ps1` | 第 1 步等待条件改为按安装目录路径过滤；其他实例记 INFO；超时日志带残留进程详情 |
| `src-main/main.ts` | 单实例锁失败路径 `app.quit()` → `app.exit(0)`（含注释同步） |
| `scripts/verify-relaunch.ps1` | C1 按 `-InstallDir` 路径过滤取进程 |

`src-main/main.ts` 的单实例锁改动**不属于**更新链路（`run_update` / `LMSLauncherUpdate` /
`cleanStaleUpdateTask` 均不动），不影响上一份 spec §改动面「node 侧不改」的结论 —— 那条针对更新链路。

## 明确不做（YAGNI）

- 不在等待超时后强杀安装目录内的进程（可能丢失用户数据；中止并由用户手动处理后重试更安全）；
- 不为「其他路径实例」做任何干预（既有的 `requestSingleInstanceLock` 才是它的正解，本 spec 已修复）；
- 不隐藏更新期间的 CMD 窗口（沿用上一份 spec 的决策）；
- 不改 `run_update` 的退出时序（`stopGraceful(3)` + 3s + `app.exit(0)` 本次实测正常）。

## 验收

1. **探针（缺陷 2）**：已有实例在跑时启动第二实例，断言其在 3 秒内退出且不留子进程（修复前 60s 仍存活）；
2. **探针（缺陷 1）**：在另一个同名实例运行时跑等待逻辑，断言立即通过（修复前必然超时）；
3. **单测**：`vitest` 全量保持绿色（`main.ts` 该改动无单测覆盖，ps1 历来靠探针验）；
4. **真机 E2E（用户执行）**：安装目录应用检测到新版本 → 下载 → 重启 → 更新脚本正常覆盖并自动拉起新版；
   验收时**故意保持另一个同名实例在运行**，正是本修复的回归场景。

## 缺陷 4（真机复测新发现）：等待通过后覆盖仍可能因文件被占用而失败

### 现象（2026-09-21 21:11 真机日志）

```
21:11:12 [INFO] 更新脚本启动 · zip=…\downloads\lms-launcher-update.zip · dir=D:\AI\LMS-Launcher
21:11:15 [INFO] 解压更新包到临时目录…
21:11:17 [INFO] 校验通过：lms_launcher.exe + resources/app.asar（25700013 字节）
21:11:17 [INFO] 覆盖安装目录…
21:11:17 [ERROR] 更新失败：文件"D:\AI\LMS-Launcher\lms_launcher.exe"正由另一进程使用，因此该进程无法访问此文件。
```

等待步骤已通过（否则不会进入解压），但覆盖目标 exe 时被占用。**这次跑的是安装目录里的旧版 ps1
（19:12:20，9280 字节，不含本规格缺陷 1 的路径过滤）** —— 与本规格缺陷 1 的修复无关，是另一个缺陷。

### 根因

**「进程枚举为空」不等于「文件可覆盖」。** `run_update` 末尾的 `app.exit(0)` 会让进程进入正在终止
状态：此时 `Get-Process -Name 'lms_launcher'` 已经枚举不到它（等待循环因此立即通过），但它仍持有
自身 exe 的文件句柄若干秒，紧随其后的 `Copy-Item -Force` 便撞上「正由另一进程使用」。

旁证（均为本次实测）：

| 观测 | 结果 | 排除了什么 |
|------|------|-----------|
| 进程完全退出后 exe 独占写权限恢复耗时 | **0.13–0.5s** | 「释放本身很慢」 |
| 计划任务上下文（同 session 1）能否看到应用的 4 个同名进程 | **能，全部可见** | 「权限/会话导致漏检」 |
| 失败后 `lms_launcher_update.log` 是否仍含 `[node]` 两行 | **仍含** | 「中途有新实例启动」——新实例的启动回显会删除整个日志文件 |

### 方案

覆盖前对关键文件（`lms_launcher.exe`、`resources\app.asar`）做**可独占写预检**：拿不到独占句柄就
每 0.5s 重试，最多 60s；仍拿不到则中止并记录诊断（含当前 `lms_launcher` 进程列表）。中止发生在覆盖
之前，安装目录保持完好 —— 不会出现 `Copy-Item` 中途失败留下的混版本目录。

### 验证（`.temp/probe-wait`，假安装目录 + 独占句柄，不触碰生产目录）

| 场景 | 结果 |
|------|------|
| 目标文件被占用 | **60.68s 后中止**，日志 `[ERROR] 目标文件被占用，60s 内无法获得独占写权限：…`，exe 未被覆盖，`__update_tmp` 已清理，退出码 1 |
| 占用已释放 | 预检通过 → `覆盖安装目录…` → exe 与 asar 均被正确覆盖，退出码 0 |

## 缺陷 5（真机复测新发现）：新版应用被绑在「更新任务」的 Job 上 —— 关掉终端会连带杀掉它

### 现象

更新成功（覆盖完成、新版启动、日志走到 `更新完成`），但：① 更新用的 CMD 终端窗口不自动关闭；
② 手动关闭该终端 → 新版应用被一起杀掉。

### 根因（实测）

`DETACHED_PROCESS` 只解决了「不继承控制台」，**没有**解决 Task Scheduler 为本次更新任务创建的
**Job Object**：

| 实测项 | 结果 |
|------|------|
| 新版应用各进程是否有控制台 | 全部**无控制台**（DETACHED 确实生效，`AttachConsole` err=6） |
| 更新脚本自身是否在该 Job 中 | **是**（`IsProcessInJob`=True） |
| DETACHED 启动的新版是否在同一 Job | **是**（继承父进程 Job） |
| `CREATE_BREAKAWAY_FROM_JOB(0x01000000)` 脱离 | **被拒**（CreateProcess 返回 err=5 ACCESS_DENIED） |
| 改走 WMI `Win32_Process.Create` | 应用**仍**在该 Job 中 |
| 改走 ShellExecute(explorer) 启动 | 应用**仍**在（各自的）Job 中 |

于是新版应用的生命周期被绑在这次更新任务上：任务因 Job 内仍有活进程而不算结束 → **终端窗口一直挂着**；
用户关闭窗口 → 任务终止 → Job 终止 → **新版应用被杀**。

> 对照组：explorer 启动的 notepad 同样 `IsProcessInJob=True` —— 说明「处在某个 Job 里」是 Windows 的
> 常态，问题在于**与更新任务共用同一个 Job**。

### 方案

第 6 步改为**独立一次性计划任务**（`LMSLauncherStart`）启动新版，由 **svchost** 拉起，落在它自己的 Job 里。
三条历史否决理由的解决：

1. **路径含空格** → 用 `schtasks /Create /XML` 导入任务定义（`<Command>`/`<WorkingDirectory>` 精确传递，
   PS 5.1「引号被剥离」的陷阱消失）；
2. **启动成败不可确认** → `/Run` 之后**轮询进程是否出现**（按 exe 全路径匹配，15s 上限），
   不再用 `sleep` 猜；任务中 `<AllowHardTerminate>false` + `<ExecutionTimeLimit>PT0S</ExecutionTimeLimit>`；
3. **任务生命周期** → 脚本**刻意不删**该任务（对正在运行的实例执行 `/Delete` 有连带终止新版的风险），
   改由应用启动时的 `cleanStaleUpdateTask` 一并清理（现在同时清 `LMSLauncherUpdate` 与 `LMSLauncherStart`）。

`DETACHED_PROCESS` 路线保留为回退（任务创建失败或 15s 内未见进程时使用）。

### 验证（真实脚本 + 假安装目录 + 自编译的常驻最小 GUI 应用）

| 断言 | 结果 |
|------|------|
| 日志 | `启动新版（独立计划任务 LMSLauncherStart，svchost 拉起）` → `新版已启动（PID 15032，独立计划任务，与本脚本的任务/控制台/Job 均无关）` → `更新完成` |
| **新版父进程** | **`svchost (PID 2696)`** —— 旧路线下是更新脚本的 powershell |
| 更新任务结束后应用是否存活 | 存活（再等 6s 仍在） |
| 任务残留 | `LMSLauncherStart` 保留（设计如此），由应用启动时清理 |
| 回归 | `npm run build` 通过；`vitest` **495/495 全绿** |
