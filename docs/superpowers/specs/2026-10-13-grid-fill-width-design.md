## 1 目标

默认 1400 窗口下，四列 + 间距恰好占满可用宽度：GPU 卡右缘距窗口右缘只剩 12px 内边距，右侧无空白；且**不因此新增横向滚动条区间**。

## 2 非目标

- 其余三列宽度、`gap`、`--card-pad`、任何卡片内部样式
- 行名截断预算 `BUDGET = 30`（`src/modules/QuickLaunch.vue:124`，旧规格 §11-1）——卡片变宽后 30 比实际可放字数（约 34 半角）保守，用户决定不改（§6-Q4）
- 窗口比 1400 更宽（最大化 / 手动拉宽）时的留白处理（§6-Q3）
- 窄窗口（<1350）的横向溢出：现状保持（旧规格 §4 已把它列为现状）
- GPU 卡宽度与切卡动画偏移（`src/style.css:561-563` 用 `100%` + 固定 32/16px，与本列宽度无关）
- 旧规格文档的改写（§6-Q6）

## 3 设计（唯一改动）

`src/style.css:80` 的 `.grid` 第 3 列（快捷启动）：`330px` → **`minmax(330px, 380px)`**。其余三列、`gap`、内边距一律不动。

改后四列上限 = 280 + 350 + 380 + 330 = **1340**，加 3×12 = **1376** = 1400 − 2×12 = 默认窗口的可用宽度 → 恰好填满。

**为什么是 `minmax(330px, 380px)` 而不是写死 `380px`**（§6-Q2）：

- 写死 380：1400 下刚好填满，但窗口宽度落在 **1350–1399** 时四列合计超出可用宽度 → 新增一段横向滚动区间（现状只有 <1350 才溢出，等于把溢出区间扩大 50px）。
- `minmax(330px, 380px)`：base = 330、growth limit = 380。网格有富余就把富余分给该列（1400 下富余 50 → 该列 380，填满）；窗口收窄时该列先缩回 330，缩到底才溢出 → **不新增横向滚动区间**，窄窗口行为与现状逐字相同。
- 上限 380 即「定宽」语义：窗口比 1400 更宽时，超出部分仍留在 GPU 卡右侧（用户决定不处理）。

**为什么只加宽第 3 列**（§6-Q1）：用户指定「增加[快速启动]卡片宽度」；第 1、2、4 列的宽度是既有定稿值（`src/style.css:78-79` 的注释记录了 2026-09/10 的定稿过程），本次不动。

## 4 验收

### 4.1 自动化契约测试（先红后绿）

位置：`src/App.test.ts`，紧邻既有网格用例（`src/App.test.ts:891-933`）。断言的是 **`src/style.css` 的规则文本**——先例：`src/modules/LogPanel.test.ts:365`（happy-dom 不加载外部 CSS，布局契约只能断规则文本）。三条：

1. `grid-template-columns` 的四个 track 逐字 = `280px` / `350px` / **`minmax(330px, 380px)`** / `330px`（第 3 列不含 `fr` → 不会无限拉伸；base 330 → 窄窗口先缩再溢出）
2. **不留空是算术**：四列上限之和 + 3×`--card-gap` = 默认窗口宽 − 2×内边距。默认窗口宽从 `src-main/main.ts` 现读（不写死 1400），内边距从 `.layout` 规则的 `padding: var(--card-gap)` 现读 → 日后任何人改窗口宽或改任一列宽，这条都会红
3. 其余三列仍是 `280px` / `350px` / `330px`（防顺手扩范围）

### 4.2 真机目视门（用户执行）

本实现环境起不了 Electron GUI（旧规格 `2026-10-10-quick-launch-card-design.md:7` 记录：`electron.exe` 立即退出 `0x80000003 STATUS_BREAKPOINT`），所以只能由用户在真机看。清单（≤5 步）：

## 7. 修订（2026-10-13，用户改口径）：第 3 列取**定宽** `380px`

用户看过实现后决定：「其他卡片没有 min 宽度，这个 [快捷启动] 卡片也固定宽度吧，直接实现，无需 SDD 流程」。

- **本节取代 §3 的 `minmax(330px, 380px)` 与 §6-Q2**：最终取值 = `grid-template-columns: 280px 350px 380px 330px;`（四列全部定宽，与其它三列写法一致）。
- **目标不变**：§1「默认 1400×950 下不留空白」仍成立，且 §4.1-2 的算术断言原样通过（`280+350+380+330 + 3×12 = 1376 = 1400 − 2×12`）。
- **接受的代价（显式登记）**：§6-Q2 当初选 `minmax` 的唯一理由消失——窗口比 1400 窄时整行不再先收缩，而是**出横向滚动条**，该区间从 `<1350` 扩到 `<1400`。用户看过这条代价后仍选定宽，故视为接受，不再作为缺陷处理。
- **§4.2 真机清单第 3 条随之改写**：原「拖到约 1360 仍无横向滚动条」作废，改为「拖到 1400 以下出横向滚动条属接受现状；快捷启动列宽恒为 380」。
- 流程口径：本次改动由用户明确豁免工作流（「直接实现，无需 SDD 流程」），故未走 `grill-me` / `brainstorming` / `writing-plans`；但按 SDD「spec 落后于代码就算缺陷」，规格、计划、check 表在同一轮内同步（见索引 K13）。
