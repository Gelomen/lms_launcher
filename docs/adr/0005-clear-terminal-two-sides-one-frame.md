# 清空终端的语义：客户端清完缓冲还要让 shell 自己清屏——xterm 与 ConPTY 必须在同一个坐标框里

终端页签的画布由两边共同写：xterm（客户端，持有缓冲与滚动区）与伪控制台（ConPTY 的 pseudoconsole 模式，它自己**不存**历史，只按**窗口内行号**发绝对光标定位）。任何一边单独动、另一边仍按旧行号定位的动作，都会在画布上留下空白错位——#33 是换行列那一拍，#34 是清屏这一拍（[清空终端] 之后手动敲命令，画布上方先空一大截才出输出）。我们决定：**[清空终端] 是两步**——先 `term.clear()` 当场清掉本实例的 buffer 与滚动区（规格 §9.1 的口径不变），再往 PTY 发一个 Ctrl+L（`onInput(id, '\x0c')`）让 shell 自己清屏，伪控制台的行号跟着回到窗口第 1 行，两边从此同一个坐标框；PTY 已停时只走第一步。

## Considered Options

### 只 `term.clear()`（最初的实现）

否。伪控制台不知道屏幕被清过，下一次重画输入行仍按它清空前的窗口行号发绝对定位（实测 120×27 那一段读数：`ESC[27;34H` ×多次），命令沉到缓冲最后一行、上面一整片空白（复放读数：row0 = 保留的旧提示符、row1..25 全空、row26 = 命令）。

### 只发 Ctrl+L（不清客户端缓冲）

否。等 shell 回包的那一拍画布还是满的，用户点完没有「当场清空」的即时感；而且 shell 已停或正被一个不认 Ctrl+L 的程序占着时，这颗按钮就彻底失效。保留 `term.clear()` 打底，最坏情况只剩「坐标框那一拍没对齐」。

### 拿 resize 往返去逼 ConPTY 整屏重绘

否（#33 已经知道行数一变它就整屏重画）。它会把**清空前**的内容画回来，等于撤销这次清空。实测只有 shell 侧清屏能把行号归回第 1 行。

### 直接喂一段「清屏」转义给 PTY

否。发往 PTY 的字节是喂给 shell 的，不是喂给 xterm 的；`ESC[2J` / `ESC[3J` 这类只有 xterm 认，pwsh 与 PSReadLine 不认。清屏要用 shell 本来就认的那个键——用户自己按 Ctrl+L 从来不出这个问题，靠的正是同一个机制。

### 可执行程序（exe）条目要不要另想办法

不存在这个问题：终端页签只可能来自 `shell` 条目（`ql_start` 对 exe 返回 `tabId: null` → 外壳不建页签；术语表「快捷启动类型」也写明 exe 没有终端），所以这颗按钮发往 PTY 的字节一定是喂给 shell 的。

## Consequences

- 「清空终端」自此**同时触碰两个真相源**（客户端缓冲 + shell 的清屏），改这颗按钮的人两步都得留着。门分两层：打桩套件钉「`clear()` 一次且 `onInput(id, '\x0c')`」与「PTY 已停就不发字节」；`TerminalTabView.clear.test.ts`（真 xterm + 写死的伪控制台坐标模型）钉画布形态与其负对偶（只清客户端 → 内容沉到画布下缘、上方空 ≥10 行）。摘掉发 Ctrl+L 那一行，正判据当场红（变异验证过）。
- 「画布上出现空白」自此有一族名字：**客户端状态与 ConPTY 坐标框脱钩**（#33 = 换行列的先后，#34 = 清屏要不要让 shell 也清）。以后任何动到 xterm 行列或缓冲的动作，都要问一句「伪控制台那一侧的行号跟着动了没有」。
- [清空终端] 在已停的页签上仍是**纯客户端**动作：`ql_write` 对没有实例的 id 抛 STATE，不为这一趟 IPC 空跑。
- 验证缺口如实登记：单测里的伪控制台是**照实测读数写死的模型**（`.temp/fs-clip/raw6-keys.chunks.json`，真 node-pty + 真 pwsh 逐键敲出来的），不是真 ConPTY；「真机上清空后敲命令不再空一截」归 #34 的真机读数门（用户按原四步复看）。 **2026-10-26 补记**：#34 的真机读数门已通过并关闭（四步复看逐条登记在 https://github.com/Gelomen/lms_launcher/issues/34#issuecomment-6420155950；同日 #35 的真机门顺带复看过一次，这条口径没被那次重写回归）。
- 与 ADR 0001 / 0002 / 0003 / 0004 不冲突：配色、页签镜像、复制粘贴语义、内容列四条一行不动。
