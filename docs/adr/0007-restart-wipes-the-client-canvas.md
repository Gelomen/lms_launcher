# 重新启动的清理：客户端整块换新（reset），对面那个全新的伪控制台不用动

终端页签那块画布由两边共同写（ADR 0005 / 0006 的同一套账）。[快捷启动] 的 [停止] → [重新启动] 那一拍，**客户端这边保活、对侧整块换掉**：页签与它的 xterm 缓冲在停止与启动之间不重建（LogPanel 的 v-show + 规格 §7.5「进程退出 / 停止 → 页签保留」），主进程却把 PTY 重建了一个（80×24 兜底，随后 App 的 `fit(true)` 强制重报真实尺寸）。新会话不认识客户端攒着的那段历史，也不会替它删：实测四款终端（pwsh / powershell / cmd / wsl）新建 PTY 的第一段都是 16B 纯转义序列 `ESC[?9001h ESC[?1004h`（t=40~310ms，与 ADR/票 #36 那条读数同源），紧随 `ESC[2J` + home + 横幅 + 提示符，**有 `ESC[2J`、没有 `ESC[3J`**；而 xterm 5.5.0 的 `ESC[2J` 只把「视口那 rows 行」抹平（`InputHandler.eraseInDisplay` case 2 → `_resetBufferLine(j)` 取的是 `lines.get(**ybase** + y)`），视口之上的历史一条不动 —— 真删历史的只有 case 3（`ESC[3J`），新会话从不发。于是每重启一次，缓冲里就多**一段**新会话的屏，旧那段的横幅与提示符留在上面 = 用户贴的那一串「`PS …> ls`」；画布上多出来的那一截空白是同一脱钩的另一头。我们决定：**[重新启动] 之前，客户端把自己的画布整块换新**（`TerminalTabView.clearForRestart`：`term.reset()` + 复位查找态 + 作废在途那一轮的尺寸账），由 App 在 `doQlStart` 里、`invoke('ql_start')` **之前**触发，判据 = 该条目正开着终端页签且此刻没有进程（`running` / `stopping` 都没有）。**ADR 0005 那两步在这一拍只剩「客户端清缓冲」这一半**：对面那个伪控制台是刚建的，它那一屏本来就是空的、行号本来就在窗口第 1 行，不需要也不该再补一发 Ctrl+L。

## Considered Options

### 什么都不做，让新会话的 `ESC[2J` 去清

否。它抹的是 xterm **视口**那 `rows` 行（`ybase` 起算），不是「那个新会话的每一行」；视口之上的历史一条不动，而每一轮整屏重绘又把缓冲底缘往下顶一整屏。复放读数（真 xterm + 写死的伪控制台字节，`TerminalTabView.restart.test.ts` 的机理格）：三趟之后缓冲里整齐地叠着三段「横幅 + 提示符」，正是用户贴的形状。

### 复用 [清空终端] 那颗的 `clear()` + Ctrl+L（ADR 0005 的两步）

否，两步都不取。`clear()` 把**光标那一行**留作第 0 行（`@xterm/xterm` 5.5.0 `browser/Terminal.ts:1224-1231`），留下的正是旧会话最后那条提示符——正是这张票要清掉的东西（把 `reset()` 换成 `clear()`，门当场红：「清完画布还剩内容 = 1」）。Ctrl+L 更不该发：对面还没开始读行，写进去的字节会撞上 #36 那一格（规范模式下被内核回显一遍）。这一拍的对手不是「同一个 shell 的坐标框」，而是「客户端攒着的历史 vs 一个全新的伪控制台」。

### 关掉页签再重建（换一个新 xterm 组件）

否。页签与终端的保活是既定的（`v-show`，卸载即 `unregister` + `term.dispose()`），关掉再重建会顺手改掉用户的滚动位与配色快照，也把「同一页签再次启动 → `fit(true)` 强制重报」那条既有口径（索引 K11(2) / K24(1)）整条推翻。

### 清在 `ql_start` 返回之后

否。那一刻新会话可能已经画了一段（第一块输出实测 40~310ms），清晚了就连新会话那一段一起抹。「清在 IPC 之前」是硬时序：`ql_start` 吊在途时读那颗计数即可判定（门 = `the_clean_up_is_done_while_ql_start_is_still_in_flight`）。代价如实登记：`ql_start` 失败时画布已经空了——旧进程本来就停着，那一屏属于已经死掉的会话。

### 停止那一拍顺手清

否。规格 §7.5 的「停止后页签保留」留着最后一屏，正是要用户能看见刚跑完/刚报错那一段（门 = `restart_clears_the_canvas_once_and_never_writes_to_the_pty` 里「停止就清画布」那一格）。

## Consequences

- 「重新启动」自此有主：`App.doQlStart`（两条入口——列表行 [启动] 与终端工具条 [重新启动]——同一个出口）在发 `ql_start` 之前调 `terminalViews.get(tabId).clearForRestart()`。加新的启动入口就得带上这一句。
- 页签的 xterm handle 自此是三面（`fit` / `focus` / `clearForRestart`），`TerminalViewHandle` 跟着改。
- 「客户端状态与 ConPTY 坐标框脱钩」这一族自此多一格：**对侧整块换掉而客户端保活**（#34 = 清屏要不要让 shell 也清；#33/#35 = 换行列的先后；#37 = 换 PTY 要不要清客户端）。以后任何「对面换了」的动作都要问一句「客户端那几行历史跟着清了吗」。
- `term.reset()` 会带出一发**焦点报告**字节（开着 `ESC[?1004h` 时进出焦点发 `ESC[I` / `ESC[O`，`browser/Terminal.ts:295` / `:1283`）。组件不拦它（那要改 `onData` 的契约），因为清画布那一拍对侧没有进程，App 的 `terminalWritable` 把它挡在 IPC 之前——门 = 「清画布那一拍不发 `ql_write`」。
- 验证缺口照旧如实登记：门里的字节是**照实测写死的伪控制台模型**（`conptyBoot` / `conptyRepaintBlank`），不是真 ConPTY；「真机上重启后画布是干净的」归 #37 的真机读数门（四款终端各一遍）。
- 与 ADR 0001 / 0002 / 0003 / 0004 不冲突：配色、页签镜像、复制粘贴语义、内容列一条不动。ADR 0005 的两步口径不改，只是这一拍只适用其中一半。
